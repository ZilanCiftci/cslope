# issue: one that can be acted on

The bar is "Issues written by Claude" in [.claude/workflow.md](../../workflow.md). A hook (`.claude/hooks/check-issue.ts`) blocks `issue_write` calls whose body lacks the required sections; this skill is how to meet them, not how to get past the hook.

## 1. Check it is new

Search open and closed issues for the same problem (GitHub MCP `search_issues` / `list_issues`). If one exists, add what you found to it as a comment instead.

## 2. Gather the evidence

- **Reproduce it** on current main: note `git rev-parse --short origin/main`, the OS, the example or synthetic model, the steps.
- **Measure** what can be measured (px, values, counts, timings) and note the date.
- **Screenshots**: capture the scene with the design-review runner (light and dark when it is about looks) or the media-capture runner; crop to the problem (python3 with PIL), keep each under ~300 kB. Never a client's project.
- Put the images on the `issue-assets` orphan branch, in `issue-<n>/` (the number after creation; use `pending-<slug>/` before and move it after), commit and push:

  ```
  git -C /home/user/cslope fetch origin issue-assets
  git -C /home/user/cslope worktree add /home/user/cslope-assets issue-assets   # or: worktree add --orphan -b issue-assets … the first time
  cp <crops> /home/user/cslope-assets/issue-<n>/ && git -C /home/user/cslope-assets add -A && git -C /home/user/cslope-assets commit -m "Images for #<n>" && git -C /home/user/cslope-assets push
  ```

  Link: `![what it shows](https://raw.githubusercontent.com/ZilanCiftci/cslope/issue-assets/issue-<n>/<file>.png)`.
- Output (a test failure, a log, a stack) goes in a code block, trimmed to the relevant lines.

## 3. Find the cause

Read the code; give `path:line`. Mark it **confirmed** (reproduced and the line found) or **hypothesis until measured**. A hypothesis makes step 0 of the plan "measure".

## 4. Write it

Title: what is wrong, where (`Sensitivity window: a scroll bar shows although the content fits`). English, sentence case, no names of other programs. Body, with exactly these `##` headings:

```
## Summary
## Steps to reproduce          (bug, wrong-result, import-export)
## Observed                    (dated; evidence: screenshots, output, values)
## Cause                       (path:line; confirmed or hypothesis until measured)
## Plan                        (numbered steps with sizes; options and rejected ones)
## Decisions for the maintainer   (only when needed; each with a recommendation)
## Done when                   (- [ ] checklist)
## Related
```

Labels: one type, a size, an area when it fits, `needs-decision` when the plan has a choice. End the body with the "Generated by Claude Code" footer.

## 5. Check before sending

- Could a sprint agent fix it from the issue alone, without asking? If not, what is missing?
- Is every claim in "Observed" something that was seen or measured?
- Does "Done when" say how to prove it fixed (a test, a measured value, a screenshot)?
